# CacheScope UI

Веб-интерфейс для запуска экспериментов, просмотра и сравнения результатов моделирования кэш-памяти в проекте CacheScope.

UI состоит из трёх частей:

- **Загрузка программы** — отправка MLIR и NPZ, выбор функции, привязка аргументов и настройка иерархии кэшей. Компиляцию, исполнение и симуляцию выполняет backend. Доступна при запуске полного приложения (Docker).
- **Статистика** — просмотр метрик кэша и сравнение вариантов программы по готовым результатам. Результат можно сохранить в автономный HTML-отчёт.
- **Пошаговая симуляция** — выполнение trace по одному событию с просмотром физического состояния кэша. Требует запущенного backend (runner) и доступна везде, где этот backend есть.

## Где что доступно

| Режим | Загрузка программы | Статистика | Пошаговая симуляция |
| --- | :---: | :---: | :---: |
| Docker (`docker compose up --build`) | да | да | да |
| Разработка (`npm run dev` + backend на 9055) | да | да | да |
| Сборка (`npm run build`, `dist/`) | да, если её отдаёт backend | да | да, если backend доступен |
| Автономный HTML-отчёт | нет | да | нет |

Пошаговая симуляция работает через HTTP API backend, поэтому доступна в Docker, в dev-режиме и в собранном приложении — везде, где есть runner. В автономном HTML-отчёте её нет: файл открывается без backend. Адрес `/?view=stepper` в отчёте открывает обычную страницу статистики.

## Запуск в Docker

Из корня репозитория:

```bash
docker compose up --build
```

Затем откройте <http://localhost:9055>. Интерфейс принимает **MLIR и NPZ**, позволяет выбрать функцию, привязать тензоры и настроить иерархию кэшей. Компиляция, исполнение и симуляция выполняются backend, а прогресс и готовый отчёт остаются на той же странице. [Готовый пример](../examples/ui-upload/README.md), [API экспериментов](../docs/EXPERIMENT_API.md).

Готовый автономный отчёт уже находится в [output/product-e2e/report.html](../output/product-e2e/report.html): скачайте его через **Download raw file** и откройте в браузере без установки зависимостей. [Инструкция и данные эксперимента](../output/product-e2e/README.md).

## Запуск в режиме разработки

Требуется Node.js `^20.19.0` или `>=22.12.0` и npm.

```bash
cd ui
npm ci
npm run dev
```

Vite выведет адрес локального сервера в терминале. Запросы `/api` проксируются на backend по адресу `http://127.0.0.1:9055`, поэтому для загрузки программы и пошаговой симуляции backend должен быть запущен (см. [runner/README.md](../runner/README.md)).

Для просмотра готового эксперимента backend не нужен: выберите папку `output/<experiment>/` в блоке выбора папки.

## Возможности

- **Загрузка программы** — MLIR и NPZ через браузер, выбор функции, привязка аргументов к массивам NPZ или нулевому заполнению, настройка уровней кэша, ограничения по времени и числу событий, прогресс и отмена.
- **Загрузка готовых экспериментов** — импорт директории с результатами через выбор папки в браузере.
- **Общая статистика** — количество обращений к линиям кэша, попадания (`hits`), промахи (`misses`), вытеснения (`evictions`) и обратные записи (`writebacks`), в том числе отдельно для чтения и записи.
- **Hit rate и miss rate** — доли попаданий и промахов, рассчитанные отдельно для каждого уровня кэша.
- **Иерархия кэшей** — переключение между уровнями (L1, L2 и другими, если они есть в данных), политики иерархии и статистика обращений к памяти.
- **Сравнение вариантов** — таблица с дельтами hit rate и числа промахов относительно базового варианта (`baseline`, а если его нет — первого в списке). Варианты группируются по одинаковой конфигурации кэша и иерархии.
- **Поинструкционная статистика** — результаты для отдельных обращений к памяти (`access_id`), если в данных есть поле `instructions`.
- **Проверка согласованности** — предупреждения о противоречиях в счётчиках, о расхождении `cache_config` и `levels`, а также о проблемах с trace: он усечён, помечен невалидным или число событий не совпадает с числом, обработанным симулятором.
- **Автономные HTML-отчёты** — один HTML-файл с интерфейсом и данными эксперимента; открывается без сервера.
- **Пошаговая симуляция** — по шагам: текущее событие, результаты по уровням, вытеснения, MLIR-исходник с подсветкой позиции, физическое состояние sets/ways, тепловая карта sets, лента hit/miss по шагам, накопленная статистика и журнал запросов к backend. Файлы `trace.json` и MLIR загружаются на backend через браузер, поэтому stepper работает и в Docker.

## Профили процессоров и ручная конфигурация

Доступны два профиля **встроенного объединённого L1**. Внешний L2 зависит
от платы и в них не включён; межуровневой связи нет.

| Процессор и режим | Размер | Строка | Ways | Замещение | Запись | Промах записи |
|---|---|---|---|---|---|---|
| IntelDX2 | 8 KiB | 16 B | 4 | Intel tree-PLRU | write-through | no-write-allocate |
| Write-Back Enhanced IntelDX4, Enhanced Bus Mode / WB | 16 KiB | 16 B | 4 | Intel tree-PLRU | write-back | no-write-allocate |

Источники: [Intel 273021-001, §7.1–7.1.2](https://bitsavers.trailing-edge.com/components/intel/80486/273021-001_Embedded_Intel486_Processor_Family_Developers_Manual_199710.pdf#page=179),
[§7.5, рис. 7-2](https://bitsavers.trailing-edge.com/components/intel/80486/273021-001_Embedded_Intel486_Processor_Family_Developers_Manual_199710.pdf#page=186),
[табл. 7-6: промах без allocation в WB-режиме](https://bitsavers.trailing-edge.com/components/intel/80486/273021-001_Embedded_Intel486_Processor_Family_Developers_Manual_199710.pdf#page=194).
Ссылки для каждого параметра, условия выбранного режима и причины исключения
прежних профилей — в [проверке профилей](../docs/PROCESSOR_PRESET_AUDIT.md).
Те же источники доступны под выбором процессора в UI.

Профили задают кэшируемую память при включённом кэше; DX4 — private-линии E/M
при WB/WT#=1, PWT=0. Трасса учитывает данные, без выборки команд, snoop и
тайминга шин. Это модель встроенного L1 указанного процессора в выбранном режиме.

Все поля можно менять вручную. Правка снимает выбор профиля; повторный выбор
восстанавливает его настройки. `PLRU4` реализует дерево Intel и требует ровно
четыре ways; при выборе этой политики UI устанавливает ways=4.

Ручные настройки:

- capacity, строка, ways; LRU/FIFO/Random/PLRU4 и seed для Random;
- write-back / write-through и write-allocate / no-write-allocate для каждого уровня;
- exclusive / inclusive / NINE для каждой соседней пары;
- передача чистых вытеснений вниз; для exclusive она обязательна;
- NINE: заполнение нижних уровней при demand fetch либо только при вытеснении.

Конфигурация сохраняется в эксперименте и восстанавливается после reload.
Старый `cache_profile` удалённого профиля не возвращает процессор в список:
его фактические `levels` и `hierarchy` загружаются как ручные настройки.

Отчёт показывает политики, локальные hit rates, back invalidations и memory
reads/writes/write bytes/writebacks. Старые отчёты по-прежнему загружаются;
отсутствующие новые счётчики показаны как «—». Финальный flush не выполняется.
Полная семантика — в [описании моделей](../docs/CACHE_MODELS.md#политики-записи-и-иерархии).

## Входные данные

Для импорта готового эксперимента UI работает с результатами, подготовленными другими компонентами CacheScope. Для загрузки программы используется отдельный [API экспериментов](../docs/EXPERIMENT_API.md); браузер не исполняет MLIR сам.

Ожидаемая структура директории эксперимента:

```text
output/<experiment>/
├── baseline/
│   └── trace.json
├── tile4/
│   └── trace.json
├── tile4-ikj/
│   └── trace.json
└── simulation/
    ├── baseline-l1/
    │   └── statistics.json
    ├── tile4-l1/
    │   └── statistics.json
    └── tile4-ikj-l1/
        └── statistics.json
```

Названия вариантов приведены для примера. UI ищет файлы по шаблонам `simulation/*/statistics.json` и `<variant>/trace.json`, а trace сопоставляет со статистикой по полю `variant`. Другие файлы в директории (`summary.json`, `events.json` и т. п.) UI не читает.

Источники данных:

- `statistics.json` — результаты симуляции, сформированные cache emulator. Обязателен: без него нечего показывать.
- `trace.json` — trace, сформированный compiler trace producer. Необязателен: UI читает только заголовок (`total_events`, `recorded_events`, `truncated`) и использует его для проверки полноты данных. Без trace статистика всё равно отображается.

Поддерживаемые схемы:

- `cachescope.trace.v1`;
- `cachescope.simulation-statistics.v1`.

UI проверяет файлы на соответствие схемам. Недоступные необязательные данные отображаются как «—», а не как нули. Файлы, не прошедшие проверку, перечисляются в блоке «Ошибки чтения».

## Пошаговая симуляция

Страница доступна по адресу `/?view=stepper`; ссылка «Пошаговая симуляция →» есть в заголовке основной страницы. Работает в Docker, в dev-режиме и в собранном приложении — везде, где есть backend (runner). В автономном HTML-отчёте ссылки нет.

Для работы нужен backend (runner) с HTTP API на `http://127.0.0.1:9055/api/v1` (адрес можно изменить в форме новой сессии).

1. В поле «Файлы трассировки» выберите `trace.json` и, при необходимости, MLIR-файлы стадий (`.mlir`). Файлы передаются на backend по HTTP (`POST /api/v1/uploads`) и сохраняются во временную директорию внутри контейнера. Backend возвращает `trace_path`, который используется для создания сессии; MLIR-файлы читаются через `GET /api/v1/source`.
2. Задайте конфигурацию кэша: для каждого уровня — имя, размер, размер линии, associativity и политику вытеснения (`LRU`, `FIFO`, `Random`, `PLRU4`). Размер линии должен быть одинаковым на всех уровнях, а число sets (`size / (line_size × associativity)`) — степенью двойки. Доступны пресеты процессоров (IntelDX2, IntelDX4) с готовыми настройками; выбор пресета заполняет поля уровня, дальнейшая ручная правка снимает выбор.
3. Нажмите «Создать сессию» и выполняйте шаги: «Следующий шаг» выполняет одно событие, «Пропустить N» — N событий одним запросом. «Сбросить» возвращает сессию в начало, «Закрыть сессию» завершает её.

В dev-режиме (`npm run dev`) запросы `/api` проксируются на `127.0.0.1:9055`; в Docker UI и runner находятся в одном контейнере, и оба эндпоинта доступны по тому же origin.

## Генерация HTML-отчёта

Перейдите в директорию `ui` и выполните:

```bash
npm run report -- --input ../output/experiment --output ../reports/experiment.html
```

Параметры:

- `--input` (`-i`) — путь к директории эксперимента (обязательный);
- `--output` (`-o`) — путь и имя создаваемого HTML-файла (по умолчанию `report.html` в текущей директории);
- `--help` (`-h`) — краткая справка.

Перед генерацией автоматически выполняется сборка интерфейса.

Пример для демонстрационного эксперимента:

```bash
npm run report -- --input fixtures/demo --output ../reports/demo.html
```

Результатом будет файл `demo.html` с интерфейсом CacheScope и встроенными данными эксперимента. Его можно открыть непосредственно в браузере или передать другому пользователю — Vite и Node.js для просмотра не нужны. В отчёте нет выбора папки, загрузки программы и пошаговой симуляции.

Полный сценарий compiler → simulator → UI из корня репозитория создаёт experiment bundle и вызывает этот генератор:

```bash
python3 examples/product-e2e/run.py
```

Итоговый файл — `output/product-e2e/report.html`, текстовая сводка с дельтами — `output/product-e2e/RESULTS.md`.

## Ограничения

- Загрузка программы поддерживает статические identity-layout `memref<f32>` аргументы, без возвращаемых значений; NPZ содержит float32 массивы соответствующей формы.
- Для просмотра статистики необходим `statistics.json`.
- Поинструкционная статистика доступна только при наличии поля `instructions`.
- Hit rate и miss rate считаются отдельно для каждого уровня; показатели разных уровней не суммируются.
- Если trace усечён, счётчики неполные и сравнение вариантов некорректно — UI предупреждает об этом.
- UI не оценивает wall-clock performance и количество CPU cycles.
- Автономный отчёт содержит данные только одного эксперимента.
- Пошаговая симуляция требует запущенного backend (runner). Загруженные файлы (`trace.json` и MLIR) хранятся во временной директории внутри контейнера и не сохраняются между перезапусками backend.
