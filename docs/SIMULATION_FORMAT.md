# Формат результатов симуляции: `cachescope.simulation-statistics.v1`

Симулятор кэша принимает `cachescope.trace.v1` и конфигурацию кэша, выполняет симуляцию и сохраняет результаты отдельно от исходной trace.

Для каждого эксперимента, конфигурации кэша и варианта создаётся отдельная директория:

```text
output/<experiment>/
  simulation/
    <config-name>/
      statistics.json
      events.json
```

- `statistics.json` — обязательная сводная статистика.
- `events.json` — необязательные результаты отдельных обращений к кэшу.

Все пути к файлам указываются относительно `output/<experiment>/`.

## 1. Статистика

`statistics.json` содержит итоговые результаты одного запуска симуляции.

```json
{
  "schema": "cachescope.simulation-statistics.v1",
  "variant": "baseline",
  "producer": "instrumented-mlir-execution",

  "cache_config": {
    "size_bytes": 32768,
    "line_size_bytes": 64,
    "associativity": 8,
    "set_count": 64,
    "replacement_policy": "LRU"
  },

  "processed": {
    "trace_events": 10000,
    "line_accesses": 18000
  },

  "totals": {
    "read_line_accesses": 12000,
    "write_line_accesses": 6000,
    "hits": 12000,
    "misses": 6000,
    "read_hits": 8000,
    "read_misses": 4000,
    "write_hits": 4000,
    "write_misses": 2000,
    "evictions": 400
  }
}
```

Значения в примере иллюстративные.

### Header

| Поле | Тип | Описание |
|---|---|---|
| `schema` | string | версия формата |
| `variant` | string | вариант, например `baseline` или `tile4` |
| `producer` | string | источник trace |
| `cache_config` | object | конфигурация кэша |
| `processed` | object | количество обработанных событий |
| `totals` | object | итоговые счётчики |

### Cache configuration

| Поле | Тип | Описание |
|---|---|---|
| `size_bytes` | integer | общая ёмкость кэша в байтах |
| `line_size_bytes` | integer | размер строки кэша |
| `associativity` | integer | количество ways в одном set |
| `set_count` | integer | количество наборов |
| `replacement_policy` | string | политика замещения, например `LRU` |

Указываются фактические значения конфигурации, использованной при симуляции.

### Processed

| Поле | Тип | Описание |
|---|---|---|
| `trace_events` | integer | количество обработанных событий исходной trace |
| `line_accesses` | integer | общее количество обращений к строкам кэша |

Одно событие trace может затрагивать несколько строк кэша, если диапазон адресов пересекает границу cache line.

### Totals

| Поле | Тип | Описание |
|---|---|---|
| `read_line_accesses` | integer | количество обращений к строкам кэша для чтения |
| `write_line_accesses` | integer | количество обращений к строкам кэша для записи |
| `hits` | integer | общее количество попаданий |
| `misses` | integer | общее количество промахов |
| `read_hits` | integer | попадания при чтении |
| `read_misses` | integer | промахи при чтении |
| `write_hits` | integer | попадания при записи |
| `write_misses` | integer | промахи при записи |
| `evictions` | integer | количество вытесненных строк кэша |

Все счётчики hits и misses рассчитываются на уровне строк кэша, а не исходных событий trace.

Обязательные соотношения:

```text
hits + misses = line_accesses

read_line_accesses + write_line_accesses = line_accesses

read_hits + write_hits = hits

read_misses + write_misses = misses
```

`evictions` — количество вытеснений существующих строк. Промах не обязательно приводит к вытеснению: например, если в наборе есть свободный way.

### Rates

UI самостоятельно рассчитывает:

```text
hit_rate  = hits / line_accesses
miss_rate = misses / line_accesses
```

Результаты отображаются в процентах.

Если `line_accesses == 0`, вместо значения показывается `—`.

## 2. События (опционально)

`events.json` содержит результаты отдельных обращений к кэшу. Файл необязателен и не требуется для отображения основной статистики.

```json
{
  "schema": "cachescope.simulation-events.v1",
  "variant": "baseline",
  "events": [
    {
      "sequence": 12,
      "kind": "read",
      "address": "0x103c",
      "size_bytes": 8,
      "lines": [
        {
          "line_address": "0x1000",
          "hit": true,
          "set": 0,
          "way": 2,
          "evicted_address": null
        },
        {
          "line_address": "0x1040",
          "hit": false,
          "set": 1,
          "way": 3,
          "evicted_address": "0x2040"
        }
      ]
    }
  ]
}
```

### Event

Каждый элемент `events` соответствует одному событию исходной trace.

| Поле | Тип | Описание |
|---|---|---|
| `sequence` | integer | исходный номер события в trace |
| `kind` | string | тип операции: `read` или `write` |
| `address` | string | адрес, переданный симулятору |
| `size_bytes` | integer | размер обращения в байтах |
| `lines` | array | результаты обращения к затронутым строкам кэша |

`sequence` сохраняется из исходной trace, чтобы можно было сопоставить результат симуляции с исходным событием.

`address` содержит адрес, фактически переданный в `ICacheSimulator::read()` или `ICacheSimulator::write()`. Для `memref_offset` это адрес после применения model base.

### Line result

Каждый элемент `lines` напрямую соответствует `LineAccessResult` из API симулятора.

| API field | JSON field | Описание |
|---|---|---|
| `line_address` | `line_address` | начальный адрес строки кэша |
| `hit` | `hit` | результат обращения |
| `set` | `set` | индекс набора |
| `way` | `way` | way, содержащий строку после обращения |
| `evicted_address` | `evicted_address` | адрес вытесненной строки или `null` |

`lines` формируется из `AccessResult::lines`.

Адреса (`address`, `line_address`, `evicted_address`) сериализуются строками в шестнадцатеричном формате, чтобы избежать потери точности при работе с 64-битными значениями в JavaScript.

## 3. Правила формирования результатов

Симулятор и программа запуска должны:

- читать исходную trace без её изменения;
- передавать обращения в `ICacheSimulator::read()` и `ICacheSimulator::write()`;
- связывать каждый `AccessResult` с исходным событием trace;
- сохранять результаты каждой затронутой cache line;
- накапливать статистику во время симуляции;
- записывать отдельные результаты для каждого варианта и конфигурации кэша.

Счётчики статистики могут накапливаться непосредственно во время обработки событий. Хранить все события в памяти для расчёта `statistics.json` не требуется.

## 4. Совместимость

До появления отдельной библиотеки для проверки схем потребители должны:

- проверять точное значение `schema`;
- игнорировать неизвестные дополнительные поля;
- трактовать `null` как недоступное значение, а не как ноль;
- использовать целочисленные счётчики как источник истины для расчёта rates;
- не считать `evictions` эквивалентом `misses`;
- сохранять 64-битные адреса без потери точности.

Изменения, нарушающие смысл существующих полей, требуют новой версии схемы.

## 5. Версии схем

| Schema | Назначение |
|---|---|
| `cachescope.trace.v1` | исходная trace от compiler runtime |
| `cachescope.simulation-statistics.v1` | итоговая статистика симуляции |
| `cachescope.simulation-events.v1` | результаты отдельных обращений к кэшу |

Compiler runtime отвечает за создание trace. Cache simulator отвечает за результаты симуляции. UI использует эти данные независимо.

## 6. Расширение для иерархии кэшей

Расширение описывает несколько уровней одного запуска, например L1 → L2 → L3.
Оно добавляет поля в существующие схемы `v1`, сохраняя прежние поля и их типы.
Отдельная директория `<config-name>` соответствует конфигурации всей иерархии.

Примеры для UI: [statistics.json](../schemas/fixtures/cache-hierarchy/statistics.json) и
[events.json](../schemas/fixtures/cache-hierarchy/events.json). Это статические fixtures
с заданными исходами проверок, предназначенные для проверки формата и счётчиков.

### 6.1. Идентификаторы и статистика уровней

При наличии нескольких уровней producer добавляет в `statistics.json` массив
`levels`, упорядоченный от ближайшего к процессору уровня наружу:

| Поле элемента `levels` | Тип | Описание |
|---|---|---|
| `level` | integer | уникальный номер от 1 до N; 1 обозначает L1 |
| `name` | string | отображаемое название, например `L1D`, `L2`, `L3` |
| `cache_config` | object | конфигурация именно этого уровня, формат раздела 1 |
| `processed` | object | число исходных событий и проверок строк этого уровня |
| `totals` | object | счётчики именно этого уровня, формат раздела 1 |

Полный список содержит и уровни, до которых не дошло ни одного запроса:
их счётчики равны нулю. Номер `level` используется для связывания данных;
положение уровня нельзя определять по его названию, размеру или associativity.

Верхнеуровневые `cache_config`, `processed`, `totals` остаются представлением
**L1**, а не суммой по иерархии. Их базовые поля совпадают с полями записи
`levels` с `level = 1`. Это позволяет прежнему UI продолжать показывать один кеш.

Для каждого уровня независимо выполняются соотношения из раздела 1.
`processed.trace_events` считает исходные события, в которых проверялась хотя бы
одна строка этого уровня, один раз на событие. `processed.line_accesses` считает
отдельные проверки строк. У нижних уровней оба счётчика могут быть меньше L1.

Hit/miss относится к проверке наличия **до** заполнения или переноса строки.
Загрузка после miss не превращает этот исход в hit. Read/write breakdown
определяется исходным `event.kind`, в том числе для lookup нижнего уровня,
вызванного write-allocate. Служебные вставки, переносы и writeback не добавляют
demand hits/misses.

Проценты локальные: UI делит hits уровня на его собственные line_accesses.
Например, 50/100 попаданий L1, 30/50 L2 и 16/20 L3 означают 50% / 60% / 80%.
Для нулевого знаменателя UI показывает `—`; отсутствие запросов не является
нулевым hit rate. Producer может дополнительно передавать `hit_rate_percent`
в `totals`: число от 0 до 100 либо `null` при нуле проверок. Источником истины
для агрегации остаются целочисленные счётчики.

### 6.2. Исходы события по уровням

Если `statistics.json` содержит `levels`, соответствующий `events.json`, когда
он создаётся, содержит описание тех же уровней: `{level, name, cache_config}`.
В каждом событии добавляется `level_results` — массив объектов
`{level, lines}`, упорядоченный по номеру уровня.

В `level_results` присутствуют только уровни, реально проверенные этим событием.
Отсутствующий L2/L3 означает, что обращение туда не дошло, а не miss.
Число результатов строк может различаться между уровнями; UI группирует их
по `level`, сохраняя исходный `sequence` для связи с trace.

Верхнеуровневый `events[].lines` сохраняется и совпадает с `lines` записи
`level_results` для L1. Он содержит только результаты L1, без смешения уровней.
Старый UI может использовать его без обработки расширения.

Строки внутри `level_results[].lines` имеют поля из раздела 2. Для нижних уровней
`way` дополнительно может быть `null`: при exclusive miss строка не размещается
на этом уровне. `null` нельзя превращать в way 0. На hit way всегда целый;
на miss с фактическим заполнением way также известен. Базовый L1 `lines`
сохраняет прежний целочисленный тип `way`.

Адреса всех уровней и вытеснений сохраняют hex-строковый формат раздела 2.
Исходы запросов не являются полным журналом изменений состояния иерархии:
служебные переносы описываются отдельно, если producer предоставляет их.

### 6.3. Статистика инструкций

Producer может добавить в `statistics.json` массив `instructions`, отсортированный
по числовому `access_id`. Каждая запись содержит:

| Поле | Тип | Описание |
|---|---|---|
| `access_id` | integer | ID статического memory access из исходной trace |
| `memref_id` | integer | ID буфера исходного access site |
| `kind` | string | `read` или `write` |
| `events` | integer | число исполнений этой инструкции в trace |
| `requested_bytes` | integer | сумма size_bytes исходных событий инструкции |
| `levels` | array | `{level, processed, totals}` для каждого объявленного уровня |

В `instructions[].levels` применяются те же правила локальных счётчиков,
достигнутых событий и процентов. Уровни без запросов также включаются с нулями.
Запрошенные байты не означают traffic между кешами.

При наличии статистики инструкций события содержат `access_id` для сопоставления.
Ключ относится к исходной trace текущего запуска; сопоставление инструкций
между compiler variants этим контрактом не определяется. Если `instructions`
отсутствует, UI обозначает статистику инструкций как недоступную.

### 6.4. Вытеснения и память

`evictions` считает замещение существующих строк, в том числе при каскадном
размещении victims. Удаление строки для её продвижения в верхний уровень
само по себе не является вытеснением. Эти операции не увеличивают hits/misses.

Producer может передавать дополнительные поля:

| Поле | Смысл |
|---|---|
| `totals.writebacks`, в том числе у уровней и инструкций | число dirty victims, переданных ниже |
| `statistics.memory` | `{reads, writebacks}` — line reads из памяти и dirty writebacks в память |
| `statistics.hierarchy` | описание inclusion/write/allocation policies иерархии |
| `events[].evictions` | `{level, line_address, dirty}` для каждого фактического victim |
| `events[].memory_reads`, `events[].memory_writebacks` | обращения в память, вызванные этим событием |
| `lines[].evicted_dirty` | dirty-флаг вытесненной строки либо `null` при отсутствии victim |

Счётчики приписываются исходной инструкции, вызвавшей операции. Например,
чтение может вытеснить ранее изменённую строку и вызвать writeback.
`writebacks` уровня и `memory.writebacks` различаются: перенос dirty victim
из L1 в L2 не является записью в память. Неизвестные или неподдержанные
дополнительные счётчики следует опускать либо передавать как `null`, а не
подставлять 0. Обязательные счётчики базового формата остаются целочисленными.

### 6.5. Поведение UI и совместимость

- Нет `levels`: показывать один кеш по прежним верхнеуровневым полям.
- Есть `levels`: показывать показатели каждого уровня отдельно; не суммировать
  их hits/misses для вычисления общего процента попаданий.
- Выбор уровня использует `level` для статистики и `level_results` для timeline.
- Нет `events.json`: сводка уровней и инструкций остаётся доступной без timeline.
- Нет `instructions`: отсутствие поинструкционной статистики не означает нули.
- Незнакомые дополнительные поля игнорируются, как требует раздел 4.

Номера схем не меняются: прежние single-cache отчёты остаются валидными,
а их поля сохраняют смысл и типы. UI, реализованный только по разделам 1–5,
продолжит отображать L1 и не обязан понимать остальные уровни.
